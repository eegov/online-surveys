# Порядок работы с исходным кодом

Документ описывает, как в проекте фиксируются изменения, создаются ветки, сливаются изменения,
проверяется качество кода и выпускаются релизы. Все правила проверяются автоматически в GitHub Actions,
а ветки `master` и `dev` защищены так, что обойти проверки нельзя.

## 1. Коммиты

Сообщения коммитов пишутся по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<тип>(<область>): <описание>

[тело: что и почему изменено]

[Refs: ONL-<номер задачи>]
```

Типы:

| Тип | Когда |
|---|---|
| `feat` | новая функция для пользователя |
| `fix` | исправление ошибки |
| `test` | тесты без изменения кода программы |
| `refactor` | изменение кода без изменения поведения |
| `docs` | документация |
| `build` | сборка и зависимости (pom.xml, package.json) |
| `ci` | пайплайны GitHub Actions |
| `style` | форматирование без изменения логики |
| `perf` | производительность |
| `chore` | прочее обслуживание |
| `revert` | откат коммита |

Области: `server`, `client`, `db`, `ci`, `deps`, `docs`, `release`. Область можно не указывать.

Описание пишется с маленькой буквы, без точки в конце, заголовок не длиннее 100 символов.

Примеры:

```
feat(server): добавить проверку состояния базы данных
fix(client): не показывать ошибку до ответа сервера
ci: собирать jar только после прохождения тестов
```

Проверка сообщений:

- локально: hook `commit-msg` (husky + commitlint) отклоняет коммит с неправильным сообщением.
  Hook ставится командой `npm install` в корне репозитория;
- в CI: job `commitlint` проверяет все коммиты pull request, job `pr-title` проверяет заголовок PR.

Правила лежат в [commitlint.config.mjs](commitlint.config.mjs).

## 2. Ветвление

Используется упрощённый Git Flow с тремя видами веток:

```
ONL-5-server-skeleton ─┐
ONL-6-client-skeleton ─┼─(squash)─> dev ─(merge commit)─> master ─> тег vX.Y.Z
ONL-10-survey-crud ────┘
```

| Ветка | Назначение | Откуда берёт изменения |
|---|---|---|
| `master` | выпущенные версии; каждый релиз помечен тегом | только PR из `dev` |
| `dev` | интеграция: здесь собираются готовые задачи этапа | только PR из веток задач |
| `ONL-<N>-<описание>` | одна задача из YouGile | создаётся от `dev`, удаляется после слияния |

Имя ветки задачи: `ONL-<номер задачи в YouGile>-<краткое-описание>` в kebab-case, например
`ONL-5-server-skeleton`, `ONL-10-survey-crud`. Ошибка, найденная после слияния, оформляется задачей-дефектом
в YouGile и тоже получает свою ветку от `dev`. Имя ветки и направление PR проверяет job `branch-name`.

```bash
git switch dev
git pull
git switch -c ONL-10-survey-crud
```

Отдельных веток `release/*` и `hotfix/*` нет: разработчик один, и выпуск этапа сводится к PR из `dev`
в `master` и тегу.

## 3. Слияние

Задача попадает в `dev` только через pull request:

1. Ветка отправляется на GitHub: `git push -u origin ONL-10-survey-crud`.
2. Открывается PR в `dev`. Заголовок PR оформляется как сообщение коммита, в описании по шаблону указываются
   задача, что сделано и как проверено.
3. Проходят обязательные проверки.
4. Самопроверка по критериям готовности задачи из YouGile (колонка In Review).
5. Слияние способом **Squash and merge**: все коммиты ветки сжимаются в один коммит в `dev`, его сообщением
   становится заголовок PR. Ветка удаляется автоматически.

Если `dev` ушла вперёд, ветку задачи перед слиянием обновляют: `git merge origin/dev` или кнопка Update branch в PR.

Этап попадает в `master` PR из `dev` с заголовком вида `chore(release): этап 2 инфраструктура` и сливается
способом **Create a merge commit**. Squash здесь не подходит: после него история `dev` и `master` расходится,
и следующий PR из `dev` снова показывал бы уже выпущенные изменения.

Защита веток (rulesets на GitHub):

| Правило | `dev` | `master` |
|---|---|---|
| прямой push запрещён, изменения только через PR | да | да |
| обязательные проверки `lint`, `test`, `build`, `commitlint`, `pr-title`, `branch-name` | да | да |
| способ слияния | squash | merge commit |
| ветка PR должна быть актуальной перед слиянием | да | нет |
| линейная история | да | нет |
| запрещены force push и удаление ветки | да | да |
| исключения для администратора | нет | нет |

В `master` требование актуальности ветки выключено: после каждого merge-коммита `dev` отставала бы от
`master` на этот коммит, а обновить защищённую `dev` из `master` можно было бы только ещё одним PR.

Обязательное одобрение другим участником не включено: в проекте один разработчик, и GitHub не даёт
одобрять собственный PR.

## 4. Контроль качества кода

| Часть | Инструмент | Что проверяет | Как запустить |
|---|---|---|---|
| Сервер | Checkstyle | стиль и типичные ошибки Java, [server/config/checkstyle/checkstyle.xml](server/config/checkstyle/checkstyle.xml) | `./mvnw checkstyle:check` |
| Клиент | ESLint | ошибки TypeScript и React, правила hooks, сложность функций | `npm run lint` |
| Клиент | Prettier | единое форматирование | `npm run format:check`, исправить: `npm run format` |

Нарушения уровня error ломают сборку. Нарушения уровня warning (длинные строки, «магические числа»,
сложность метода выше 10, TODO) сборку не ломают, но считаются в метрике предупреждений линтера.

## 5. Пайплайны

| Workflow | Когда запускается | Что делает |
|---|---|---|
| [CI](.github/workflows/ci.yml) | каждый push в любую ветку, каждый PR | `lint`: Checkstyle, ESLint, Prettier. `test`: модульные и интеграционные тесты сервера (JUnit 5, Testcontainers с PostgreSQL), тесты клиента (Vitest), отчёты о покрытии JaCoCo и v8. `build`: после успешных `lint` и `test` собирает `survey-server.jar` и `dist` клиента и сохраняет их как артефакты |
| [PR checks](.github/workflows/pr-checks.yml) | каждый PR | `commitlint`, `pr-title`, `branch-name` |
| [Release](.github/workflows/release.yml) | push тега `vX.Y.Z` | полная проверка и сборка, сбор метрик, публикация GitHub Release |

Отчёты о тестах и покрытии сохраняются как артефакты запуска (`test-reports`), сводка метрик выводится
на странице запуска (Summary).

## 6. Релизы

Версии нумеруются по [SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`. Релиз выпускается
на завершение каждого этапа разработки из плана проекта:

| Версия | Этап |
|---|---|
| `v0.1.0` | 1. Прототип |
| `v0.2.0` | 2. Инфраструктура |
| `v0.3.0` | 3. Конструктор опросов |
| `v0.4.0` | 4. Публикация и прохождение |
| `v0.5.0` | 5. Результаты |
| `v0.6.0` | 6. Тестирование |
| `v1.0.0` | 7. Релиз |

Исправление ошибки в уже выпущенном этапе увеличивает PATCH: `v0.3.1`. Промежуточный срез до завершения
этапа выпускается как pre-release с суффиксом: `v0.1.0-alpha.1`.

Как выпустить релиз: слить PR из `dev` в `master`, затем поставить тег на `master`.

```bash
gh pr create --base master --head dev --title "chore(release): этап 2 инфраструктура"
# после прохождения проверок: Create a merge commit
git switch master
git pull
git tag -a v0.2.0 -m "Этап 2. Инфраструктура"
git push origin v0.2.0
```

Workflow Release проверяет и собирает проект, снимает метрики и создаёт GitHub Release, к которому
прикладывает `survey-server.jar`, `survey-client-dist.zip`, `metrics.json` и `metrics.md`. В тексте релиза
таблица метрик и список слитых PR.

## 7. Метрики качества

Метрики снимает [scripts/collect_metrics.py](scripts/collect_metrics.py) из отчётов инструментов. В каждом
запуске CI в Summary попадают метрики линтеров, тестов и покрытия. При релизе этапа собирается полный набор
и сохраняется в файлах релиза, поэтому по релизам видна динамика от этапа к этапу.

| Группа | Метрика | Источник |
|---|---|---|
| Статический анализ | ошибки и предупреждения линтера | Checkstyle, ESLint |
| Статический анализ | цикломатическая сложность (средняя и максимальная на метод) | JaCoCo |
| Тестирование | покрытие строк | JaCoCo, Vitest (v8) |
| Тестирование | покрытие ветвлений | JaCoCo, Vitest (v8) |
| Тестирование | число пройденных и упавших тестов | JUnit XML |
| Тестирование | время выполнения тестов | JUnit XML |
| Процесс | частота и размер коммитов | `git log` |
| Процесс | открытые и закрытые PR, время жизни ветки | GitHub API |
| CI/CD | время выполнения и доля успешных запусков пайплайна | GitHub API |

Снять метрики без релиза: Actions → Release → Run workflow.
